## Draft implementation plan for the HubDev Omarchy Quattro plugin
- **Status:** ✅ Completed (reviewed)
- **Scope:** planning / research · branch `main`
- **Summary:** Researched `lerd Glance`, the Omarchy Quattro plugin spec and the HubDev CLI, then drafted a phased implementation plan for `io.hubdev.buddy` and put it through an adversarial review that changed seven of its decisions.

### Changes
- Repository initialised as a planning repo — no plugin code yet, by design: Omarchy Quattro is not installed on this machine (still 3.8.5, no QuickShell, no `omarchy plugin`).
- `docs/implementation-plan.md` — full plan: reference decomposition, the HubDev/lerd gap, transport decision, JSON contract, product scope, seven phases, eight risks, the grill.
- `docs/research/hubdev-buddy-plan.html` — presentation copy, published as a private Artifact, built on HubDev's own brand palette found in `readme-drafts/`.
- `README.md` — states the planning status up front and names the one unknown the plan hangs on.

### Findings that shaped the plan
- HubDev has **no local HTTP API and no machine-readable CLI** — `--json` is silently ignored and ANSI is emitted even under `NO_COLOR`. lerd Glance's whole transport assumption does not hold here.
- `mcp.Bridge` (`devhub-go/internal/mcp/server.go`) already exposes every read the widget needs as JSON-tagged structs, so `hubdev snapshot --json` is one new `cli_snapshot.go`, not a feature. Phase 1 revised from ≈3–4 sessions to ≈1–2.
- `RunDiagnostics()` already returns `{Name, Status, Message, Detail, Icon}` — the panel's environment-health block comes free.
- **No file locking exists anywhere in `devhub-go`** (in-process `sync.RWMutex` only), which answers the concurrency question for polling reads and replaces it with a smaller pre-existing one: writes are last-writer-wins between the widget, the CLI and the GUI.
- The only `ListenAndServe` in the tree is the DNS stub, so a loopback daemon is genuinely greenfield and correctly deferred to Phase 6.

### Verification
- All findings read directly from source or measured on this machine against HubDev v1.27.0: CLI latency (`site:list` 59 ms · `service:list` 87 ms · `status` 374 ms), `NO_COLOR` behaviour, absent listening sockets (`ss -ltnp`), config state files, and the `mcp.Bridge` interface.
- Plan self-reviewed under an adversarial pass; 13 challenges recorded with verdicts, 7 folded back into the plan body.
- Artifact HTML validated for tag balance before publishing.

### Findings
- **R1 is closed twice over.** The spike does it, and `bobbynicholas.omaland` — an unrelated third-party plugin already installed on this machine — imports `Quickshell.Io`, `Quickshell.Wayland`, `qs.Ui` and `qs.Commons` today. The import question is settled where it matters.
- **R3 described a failure mode that does not exist.** `platform.RunPrivileged` (`devhub-go/internal/platform/privilege_linux.go`) is `sudo -n` (fails fast, never prompts) then `pkexec` (a *visible* polkit dialog). A QML `Process` can never hit a hidden terminal prompt; it can hit a visible dialog that still blocks. Milder, still needs the hard timeout.
- **`site:fix` is the one verb cut.** It calls `RunPrivileged("chmod","0666",sock)` — `chmod` is not in HubDev's sudoers rule — and only *conditionally*, when the FPM socket mode is already wrong. It would pass every manual test until the day it escalated.
- **`NOPASSWD: /usr/bin/bash -c *`** is the last line of the rule HubDev installs on every Linux machine. That is `NOPASSWD: ALL` written long-hand. Noted as an aside for `devhub-go`; it does not block the plugin, since every verb Buddy wants is covered by the `systemctl` line.
- **R2 was underestimated.** `service:list` probes Docker per service: 87 ms stopped → **568 ms** with 5 containers up. `status` 374 → 918 ms. Naive fan-out ≈ 3.1 s. `services` was in the plan's *cheap* 5-second tier; it is now in the expensive 30-second one, and the server-side TTL cache is load-bearing rather than optional.
- **The best scaffold is `SystemUpdate.qml`, not `agents/Panel.qml`** — 60 lines vs 32 KB, and already the exact shape (`BarWidget` base, `Process`, `Timer { triggeredOnStart }`, `BarIconButton`, `IpcHandler`).
- **Hot reload works.** Saving QML inside the plugin folder logs `Local plugin changed, reloading: <id>` and re-renders — no restart, no `rescanPlugins`. The §8 dev loop is correct as written.
- **A shell bug that is not ours:** `Bar.qml:1770 TypeError: Cannot assign to read-only property "moduleName"`. `CustomCommandModule` declares it `readonly` (`Bar.qml:1548`, `:1784`) while `injectProps()` assigns to it. Fires on any bar-slot rebuild when the layout holds a `"type": "command"` module — this machine has one (`tunnel`).

## Phase 2 — read-only widget v0.1, verified in the live bar
- **Status:** ✅ Completed (reviewed)
- **Scope:** Omarchy Quattro plugin `io.hubdev.buddy` · branch `main`
- **Summary:** Built the read-only bar widget and its QML-free core, verified all three states on screen against real fixtures, and fixed a version gate that only the live shell could expose.

### Changes
- **New plugin files** — `manifest.json`, `BarWidget.qml` (the only I/O owner), `Mark.qml` (glyph + state dot), and the pure-JS core `Model.js`, `Theme.js`, `SourceJson.js`.
  - `BarWidget.qml` owns the `Process`, a coalescing `inFlight` guard, a per-tier timeout `Timer` that terminates an overrunning child, `poll.running: root.visible` to suspend when the bar is hidden, and an `IpcHandler` for `refresh`.
  - **No separate `Source.js`.** The seam is the *import line* (`import "SourceJson.js" as Source`) — literally the one-line change §4 specifies. A dispatcher in front of it would add indirection without adding a seam. Plan §7.5 records the deviation.
- **Tests** — `test/harness.mjs` loads the real `.js` files into node, stripping only QML's `.pragma` directive, so there is no second copy to drift. **48 assertions** across `model`, `source` and `theme` suites.
- **Fixtures** — 10 files in `test/fixtures/`, generated from live `hubdev mcp` output: `healthy` (15 sites, 8 services, 2 PHP), `caddy-down`, `php-default-fpm-down`, `autostart-service-stopped`, `docker-down`, `no-sites`, `all-stopped`, `license-inactive`, `schema-future`, `minimal`.
- **`tools/hubdev-snapshot`** — reference implementation of the §4.1 contract over `hubdev mcp` + the Caddy admin API + `docker ps`. Explicitly **not** a shipping path (it is §4 approach E, rejected in G8); it exists so Phase 2 could finish before Phase 1, and it is the executable acceptance target for the Go work.
- **Version-gate fix** (`1d8c03f`) — see Findings.
- `docs/implementation-plan.md` — Phase 2 marked complete, **§7.5** added, and the §8 dev-loop claim corrected.
- `README.md`, `CLAUDE.md` — status, layout and the dev-loop correction.

### Findings
- **The version gate was broken, and only the live shell showed it.** `hubdev snapshot --json` on v1.28.0 prints `Unknown command: snapshot` plus its entire usage screen **to stdout** and **exits 1**. `parse()` only reached its "too old" branch on exit 0 with non-JSON output, so the real case fell through to *"HubDev exited with code 1"* — true, and useless in a tooltip. Every fixture had been exercising the exit-0 path. Fixed, with the real v1.28.0 output as a regression test.
- **Saved QML does NOT hot-reload an already-instantiated `bar-widget`.** This contradicts what Phase 0 recorded. The shell logs `Local plugin changed, reloading: <id>` on every save, but the running widget keeps its original code: edits had no effect, `console.log` never fired, and a deliberate syntax error loaded without complaint. **`omarchy-restart-shell` after every QML edit** is the real loop.
- **The tell was a line number.** The shell kept reporting an `IpcHandler` warning at `BarWidget.qml[154]` while the file on disk had it at `156` — a two-line offset exactly matching the two `console.log` lines added. That is the cheapest way to know which version is actually running.
- **Three rules the live data forced into `Model.js`**, each now a named test:
  - an *uninstalled* service with `auto_start: true` must not warn — `reverb` ships exactly that, and would have warned forever about something never set up;
  - a stopped Caddy reports **once**, not once per site — otherwise `all-stopped` emits fifteen identical issues;
  - an absent `route_present` means *unknown*, not missing — so a v1 contract without the PROPOSED fields still renders truthfully.
- **The mark is not monochrome.** The placeholder Nerd Font glyph resolves to a colour font, so `color: root.foreground` is ignored and it renders two-tone in any theme. §5.1's "monochrome, taking the bar foreground" is unmet until the Phase 5 mark asset lands.
- **G7 is only half closed.** `Theme.js` defines a distinct glyph per level so colour is never the sole carrier, but `Mark.qml` draws a plain coloured `Rectangle` and uses a pulse on `down` as its second channel. In a still frame `warn` and `down` differ by hue alone — the exact failure G7 predicted on this machine's amber theme.
- **A long detour that was not ours.** The bar's right section rendered nothing for most of a session; `omarchy-shell omarchy.network refresh` answered `Target not found` for a *first-party* widget, and it survived a clean shell restart. Cause: the user's own `m0u.bar` — a clone of `omarchy.bar` with the `required` host properties de-required — was mid-edit in a parallel session. Everything rendered once that work settled. The earlier suspicion that the `tunnel` command module caused it was **wrong**; `tunnel` is still present and the bar is fine.

### Verification
- `omarchy plugin validate ~/.config/omarchy/plugins/io.hubdev.buddy` → exit 0; `qmllint -I /usr/share/omarchy/shell` clean on `BarWidget.qml` and `Mark.qml`.
- `node --test 'test/*.test.mjs'` → **48/48 pass**.
- Installed as a git checkout at `~/.config/omarchy/plugins/io.hubdev.buddy` with this repo as `origin` (§8's sanctioned loop); no symlinks anywhere in the folder.
- **All three states confirmed in the live bar**, by both the widget's own log and pixel sampling of a `grim` capture:
  - `caddy-down` → `level=down dot=true`, *"Caddy is stopped — no site will resolve"*, red dot present;
