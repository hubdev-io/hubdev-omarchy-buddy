## Phase 4c — the keyboard cursor over the site list
- **Status:** ✅ Completed (reviewed)
- **Scope:** panel interaction · branch `main`
- **Summary:** Arrows walk the site rows and their actions, Enter/Space presses what the
  cursor is on, and the mouse drives that same cursor so only one highlight is ever on screen.

### Changes
- `Model.visibleSites(summary, search, expanded)` returns serving / the collapsed count /
  parked **already in draw order**. `SitesSection.qml` renders that; `Actions.navRows()` walks
  it. Neither the view nor the cursor is the authority on order any more — the value is.
- `Actions.js` gained the cursor map: `navRows`, `navCols`, `navColOf`, `navMove`, `navTarget`,
  plus `navList`/`navClamp`. It lives there rather than in a new file because the only hard
  part is the runnable gate (`siteArgv`), and `test/harness.mjs` strips `.import`, so a QML JS
  library cannot cross-import without breaking `node --test`.
- The cursor is a **key** (`site:<ref>`), never an index — the snapshot refreshes under an open
  panel and a search re-ranks on every keystroke.
- `KeyCatcher.qml` gained `moveRequested(dx, dy)` (the shared component's signature),
  `activateRequested()` for Space and `returnRequested()` for Return. Space is handled *before*
  the printable branch; it never belonged there, as the matcher folds whitespace out.
- `Panel.qml` owns `cursorKey`/`cursorCol` and `sitesExpanded`, plus `moveCursor`, `setCursor`,
  `clearCursor`, `activateCursor`, `activateReturn` and `revealRow()` (scroll-into-view).
- `SiteRow.qml` and `CollapseRow.qml` rewritten to paint from `hasCursor`/`current` rather than
  `containsMouse`, per `CursorSurface`'s documented contract. A pointer entering a row raises
  `cursorRequested` exactly as an arrow key would.
- Clamping, not wrapping, in both axes; the column survives a vertical move, clamped to what
  the new row offers.
- Space has no fallback, Return does (it opens the top search match). The collapsed
  *parked sites* count is a cursor stop, or the parked rows are unreachable without a mouse.

## Phase 4d — summon the panel from a global key
- **Status:** ✅ Completed (reviewed)
- **Scope:** bar-widget lifecycle / IPC routing · branch `main`
- **Summary:** `omarchy-shell shell toggle io.hubdev.buddy`, bound in Hyprland, opens Buddy on
  the focused output — and the one-word fix that made the plugin eligible for it repaired three
  other things nobody knew were broken.

### Changes
- **`opened`, not `panelOpen`.** `Bar.findPanelWidget` and `Bar.panelNavigationSlots` skip any
  bar slot whose item lacks `open()`, `close()` **or `opened`**, and they inspect the *widget
  root*. The old name silently cost four things: `shell toggle` answered `unknown` (no keybind
  possible); Buddy was excluded from the `SUPER+CTRL+<n>` panel numbering, which renumbers
  every panel to its right rather than leaving a gap; `Tab` — wired to `bar.switchPanelFrom`
  since Phase 3 — could never find its own slot and had never worked; and `KeyboardPanel` had
  no `popoutSwitchClosing` to read off its owner.
- `popoutSwitchClosing` forwarded from the panel alongside it.
- **`runOnFocused(verb)`.** The plugin's own `open`/`close`/`toggle` IPC routes stopped
  broadcasting: on two monitors they opened the panel on both heads. They now use the same bar
  routing `shell toggle` does, so the two entry points cannot disagree. `refresh` stays a
  broadcast — every head draws the mark.
- `refresh("full")` moved from the bar button's press handler into `open()`, so every way in
  gets current numbers. Still coalesced.
- Keybind added **outside this repo**, in `~/.config/hypr/bindings.lua`:
  `o.bind("SUPER + CTRL + J", "HubDev Buddy", "omarchy-shell shell toggle io.hubdev.buddy")`.
  `J` is arbitrary — `H` (Hardware), `B` (Bluetooth) and `D` (Display) are all stock bindings,
  so no mnemonic letter was free in Omarchy's panel family.

### Verification
- `qs ... ipc call shell togglePanelAt right 1` → **`io.hubdev.buddy`**, where it previously
  answered `omarchy.agents`.
- `omarchy-shell shell toggle io.hubdev.buddy` — the exact string the keybind runs — opens and
  closes cleanly; `summon: no live bar widget for: io.hubdev.buddy` is gone from the shell log.
- Focused-output claim proven, not assumed: with `HDMI-A-1` focused the `omarchy-keyboard-panel`
  layer maps at `0 0` and the dismiss catcher at `1920 0`; after
  `hl.dsp.focus({ monitor = "+1" })` the two swap. Focus restored afterwards.
- `npm test` 148/148 · `omarchy plugin validate .` 0 · qmllint clean · privacy clean.

### Known consequence
- Buddy sits second in the bar's right section behind the tray, which has no panel and is not
  counted — so it **is** `SUPER+CTRL+1` now, and every stock panel number shifted by one. That
  is the numbering doing what it documents ("the Nth panel icon the user can see"), but it is

## Phase 4e — start, stop and restart a service from the panel
- **Status:** ✅ Completed (reviewed)
- **Scope:** actions / service control · branch `main`
- **Summary:** The first verbs that change the machine — a `Process` with a guard timer, a
  confirm gate on `stop`, a spinner, a refusal line and a burst refresh — plus the correction
  of a HubDev field whose name had been read as meaning something it does not.

### Changes
- **`Actions.js` gained the service allowlist**: `start` · `restart` · `stop`, each a fixed
  argv, each gated against the *current* snapshot. `needsConfirm`, `timeoutMs`,
  `confirmToken`, `serviceActionLabel`, `serviceDoneLabel` and `parseResult` live there too, so
  every rule that decides what runs and what the panel says about it is under `node --test`.
- **`BarWidget.runAction(request)`** — the non-detached counterpart to `runDetached`. Its own
  `Process` (separate from the snapshot's, which has a different timeout and lifetime), a
  per-verb guard timer, `actionState` (`idle`/`running`/`done`/`failed`), a 3s success clear, a
  6s failure clear, and a **burst refresh**: one immediately, then three at 1.4s, because a
  container reports itself running before HubDev's probe agrees.
- **One action at a time**, enforced in `runAction` rather than only in the view — every other
  button dims, and a keyboard shortcut cannot walk around a guard that exists only in the UI.
- **Confirm gate on `stop` alone.** Restart drops connections but puts the service back;
  `stop` is what leaves something down until a person notices. Arming both would make two of
  three buttons on every running row take two presses, which is how a gate stops being read.
  Armed for 4s, keyed on the *button* (`svc:<name>:<verb>`), disarmed by Escape, by moving the
  cursor, by a keystroke into the search, and by reopening the panel.
- **The status line lives in the footer, not above the list.** A line above the rows pushes
  every row down by its own height — so the button you are about to press a second time moves
  out from under the pointer. One line carries all four states: refusal, question, progress,
  confirmation.
- **`ServiceRow.qml` rewritten** to the SiteRow shape: `HoverHandler` over the subtree,
  `CursorSurface` painted from the cursor and never `containsMouse`, a trailing block reserving
  the width of its widest state, a rotating spinner while busy and a red glyph where the detail
  was when it failed.
- **The keyboard cursor now walks Services.** `Model.visibleServices()` returns the buckets in
  draw order; `Actions.navServiceCols` / `navServices` extend the map. A service row has **no
  `open` column** — a domain is somewhere to go, a service is not, and Enter on the row would
  have to silently pick one of three verbs.

### The correction — `installed` does not mean "set up here"
Found by using it, not by the tests. Stopping Mailpit from the panel greyed the row out and
left no way back.

`installed` in HubDev means *"starting would be immediate"* — for a docker service, that the
container object exists — and `hubdev service:stop` **removes** the container. So the flag
flips false on every stop. `Model.js` was reading it as "one of my services" in three places,
and all three broke the moment the panel had a stop button: the row dropped into the collapsed
"not set up" group, its start button went with it, and the *"set to start automatically but is
stopped"* warning fell silent — the bar sat green with two services down.

The question is now split in two, computed once in `summarize()`:

- `configured` = `up || autoStart || immediate` — is this one of my services? Survives a stop.
- `startable` = `immediate || mode === "docker"` — can it come up without installing a package?

Grouping and the action gate use `configured`; the attention warning uses `startable`, which is
what keeps `reverb` (auto-start, native, no binary) from warning forever — the job `installed`
was doing before it turned out to mean something else. `serviceGroups` returns
`configured`/`others`/`otherCount`; `visibleServices` returns `rows`/`others`.

### Verification
- `npm test` → **191 tests, 191 pass, 0 fail** (43 new: `test/services.test.mjs` plus the
  service half of `test/keyboard.test.mjs` and the regression pair in `test/model.test.mjs`).
- New fixture `test/fixtures/stopped-by-hubdev.json` — **derived from the redacted `healthy`**,
  not captured live, so it inherits its redaction (R6). It pins the state HubDev's own stop
  leaves behind, which no existing fixture could express.
- `omarchy plugin validate .` → exit 0 · `qmllint -I /usr/share/omarchy/shell` clean ·

- Against the live machine, with Redis and Mailpit stopped by the panel: both stay in the
  Services list, both offer `start`, `reverb` is listed with no buttons, `meilisearch`/`minio`
  stay collapsed, and the issue list reads *"Redis, Mailpit are set to start automatically but

- **Exercised by the user**: stop and restart both driven from the panel on Mailpit and Redis.

### Known consequence
- Pressing `start` on a docker service whose image was pruned will re-pull it. The 90s ceiling
  is not a promise the verb finished — a killed `service:start` can leave Docker still working —
  which is why the burst refresh runs on timeout as well as on success. The snapshot, not the

## Update HubDev — an action for the one state where nothing else works

- **Status:** ✅ Completed (reviewed)
- **Scope:** panel footer · version gate · branch `main`
- **Summary:** in the "too old" state the footer's **Refresh** could only re-fail, so it is
  replaced there — and only there — by **Update HubDev**, which opens the upgrade in a terminal.

### Changes
- `SourceJson.js` refusals now carry a machine-readable `code` beside the human string:
  `"missing"` (exit 127 or a spawn failure), `"outdated"` (unknown-command, or non-JSON on a
  clean exit), `"error"` for everything else. A successful parse carries none. The panel branches
  on the code; the sentence stays the user's.
- `Model.unreachable(reason, code)` sets `outdated`, and `BarWidget.fail(reason, code)` carries it
  down **both** branches — the fresh-failure one and the merge that keeps a stale document — so
  the gate does not disappear the moment a previous good snapshot is still on screen.
- `Actions.updateArgv(summary)` returns `["omarchy-launch-tui", "hubdev", "update"]`, and `[]`
  unless `summary.outdated === true`. **Not** for "unreachable" generally: a HubDev that is
  missing or crashed is not helped by an update, and offering one there would be guessing at a
  cause the widget cannot know.
- **It opens a terminal instead of running detached.** On Arch `hubdev update` is
  `yay -Syu --noconfirm hubdev-bin` — a full unattended upgrade of the *whole system*, not of one
  package. It can take minutes, it can fail on any unrelated package, and `/etc/sudoers.d/devhub`
  makes it passwordless — so it must happen somewhere the user can watch it and stop it.
- `Theme.js` gained `"update"` → `` (nf-fa-arrow_circle_up), checked against the cmap of the
  font this machine actually loads rather than against a glyph chart.

### Verification
- 17 tests in `test/update.test.mjs`: the gate opens on `outdated` and on nothing else, the argv
  is fixed and unpoisonable, each call gets its own array, and the icon resolves to a real glyph
  distinct from Refresh.
- Seen on screen in the gate state with the packaged v1.28.0, and gone after the user installed
  v1.29.0 — both halves of the swap observed, not just the one that was easy to reach.

## devhub-go — Laravel Reverb reads as stopped outside the process that started it

- **Status:** ✅ Analysed and filed (no plugin change)
- **Scope:** upstream investigation · `hubdev-io/devhub-go`
- **Summary:** the GUI showed Reverb running and the panel showed it down; the CLI is wrong, the
  panel is faithfully reporting what it was told, and the defect is in the provider — not in
  `snapshot`.

### Findings
- `hubdev service:list` is wrong in the same way `snapshot --json` is, which locates the bug below
  both: `ReverbNativeProvider.Status()` is `p.cmd != nil && p.cmd.Process != nil` — an in-memory
  handle on the child *that process* spawned. Only the GUI has it.
- It is the **only** native provider without cross-process recovery: Mailpit, MeiliSearch and MinIO
  adopt through `liveDetachedPID` (PID file + port scan), the Windows provider through a saved PID
  and an image/port match, Redis through `systemctl is-active`. Reverb writes no PID file at all.
- `internal/provider/native_adopt_linux.go` already documents this exact failure as the reason
  those helpers exist — *"seen as stopped, fail to start with PORT_IN_USE, silently no-op on
  Stop"*. Reverb was simply never brought into the pattern.
- Worst consequence is not the wrong dot: **`hubdev service:stop reverb` returns success and does
  nothing**, because `Stop()` early-returns when `p.cmd == nil`.
- Fixing `Status()` alone would not make a CLI start work either — the Linux child gets
  `Pdeathsig: SIGTERM`, so a Reverb started by a short-lived CLI process is killed as it exits.
- Second, separate defect on the same row: `installed` is **permanently** false, because
  `isServiceInstalled` returns false for native providers exposing no `IsInstalled()` and Reverb is
  the only one without it. The check that would answer it exists and `Start()` already calls it —
  `reverb.SkeletonReady()`. Distinct from #11, which is the `docker rm` inside `service:stop`.

### Why the plugin needs no change
Verified against the live snapshot: all three verbs on the Reverb row refuse — `start` is blocked
by `startable !== true` (native, not immediate) and `stop`/`restart` by `needs: "up"` — so the
buttons draw dead and nothing fires. The bar mark stays green, correctly. A port probe in the
panel would mean the widget second-guessing its own data source, which is the maintenance debt
#11's workaround already showed the cost of.

### Verification
- `ss -ltnp` shows `php artisan reverb:start` listening on 127.0.0.1:8181 while both CLI surfaces
  report `stopped` — the mismatch reproduced from the shell, not inferred from the screenshot.
- The skeleton at `<DataDir>/reverb/skeleton` has `artisan`, `vendor/laravel/reverb` and
  `config/reverb.php`, so `SkeletonReady()` would return true today.
