01Two findings

Everything in this plan follows from two facts about HubDev

Verified against HubDev v1.27.0 on this machine, 31 August 2026.

The blocker

HubDev has no local API and no machine-readable CLI

lerd Glance is a thin QML client over an HTTP API on 127.0.0.1:7073. HubDev has no listening socket and no daemon. --json is silently ignored, and ANSI escapes are emitted even under NO_COLOR. The transport lerd's whole design rests on does not exist here.

The opening

But the JSON already exists, behind hubdev mcp

hubdev_list_services already returns {name, display, status, mode, port, version, auto_start, installed…}. The Go core models and serialises all of it. Exposing that as hubdev snapshot --json is a serialisation change, not a feature.

Confirmed in devhub-go, 31 Aug

  • mcp.Bridge is the seam that already exists. internal/mcp/server.go defines a deliberately slim interface over the main App — its own comment says the methods are "intentionally named like the bindings the GUI uses". It already carries the entire read side: SiteList, SvcList, PhpListVersions, PhpGetDefault, RunDiagnostics, NgrokListTunnels, GetVersion — every one returning a JSON-tagged struct. snapshot --json is one new cli_snapshot.go wiring the same app value cli_mcp.go already builds. No new data plumbing.
  • RunDiagnostics() hands over the health block for free. DiagnoseCheck is already {Name, Status:"ok"|"warning"|"error", Message, Detail, Icon} — exactly the Environment flags, so the bar's dot rules derive from it rather than being reinvented.
  • No HTTP server exists in HubDev. The only ListenAndServe in the tree is the DNS stub. Approach B really is greenfield, which is why it stays at Phase 6.
  • No file locking exists anywhere. Concurrency is in-process sync.RWMutex only — which answers the Phase 0 concurrency question for reads, and replaces it with a smaller, pre-existing one: writes are last-writer-wins between the widget, the CLI and the GUI.

Measured, services stopped: site:list 59 ms · service:list 87 ms · status 374 ms. Fast enough to poll — but status probes Docker, so that number grows once containers run. This is what forces the tiering in §05.

02The reference

What is worth taking from lerd Glance is architectural, not visual

Five ideas carry over unchanged:

  1. One I/O owner. Only BarWidget.qml talks to the outside. Views call run(request) and bind to what comes back. This is what makes everything else testable.
  2. Pure-JS logic. Model.js and Actions.js import nothing from QML, so node --test runs the exact files the shell loads.
  3. Quiet by default. A monochrome mark taking the bar foreground; a coloured dot only when something is wrong. Empty sections are not drawn at all.
  4. Failure lands on the row that caused it. actionState is keyed by request, so a refusal turns that row's icon red with the message as its tooltip, and self-clears after 6s.
  5. Refresh burst after a mutation. Some verbs return before the thing is up, so one refresh repaints the state you just left. Poll immediately, then twice more at 1.5s.

What must not be copied

lerd is Podman-centric — every site and service is a container, so "total CPU and memory across every container" is a meaningful headline. HubDev is hybrid: Caddy and PHP-FPM are native processes, services are per-service docker or native, sites are traditional or docker. A container-resources meter would describe a minority of what HubDev runs. It is replaced by an Environment column.

04Architecture

How the plugin gets its data

Five approaches were considered. The recommendation is a short-lived subprocess, not a daemon — the Omarchy docs are explicit that plugins run unsandboxed inside the long-running shell process and must never start a second Quickshell process.

A Recommended. Spawn the CLI from QML Process. No port, no auth design, no daemon lifecycle. hubdev snapshot --json
A′ If Process is unavailable to plugins. XHR is proven available (lerd uses it) and reads file://. A systemd user timer writes the snapshot; the plugin reads the file. Read-only, but no daemon.XHR file:// ~/.cache/hubdev/snapshot.json
B Last resort. A loopback HTTP daemon in HubDev — lerd's exact shape, and the biggest change. Deferred to Phase 6. XHR http:// — hubdev api
C Rejected. JSON-RPC to a long-lived hubdev mcp child. MCP is an agent protocol with a master off-switch whose entire purpose is refusing sessions.
D / E Spike only. Parse the ANSI tables, or read the config YAML plus Caddy :2019 plus docker ps directly. Both reimplement HubDev's own resolution logic in a second place, where it will drift.

All of them live behind one seam. Source.js exposes a single snapshot(cb) returning the canonical shape, so swapping SourceJson ↔ SourceFiles ↔ SourceHttp changes one line in the widget and nothing in Model.js, the views, or the tests.

05The contract

One aggregate call, tiered, with the secrets stripped

lerd fans out to seven endpoints because HTTP round-trips are cheap. Process spawns are not — so this is one call, and the expensive half of it never runs at 5 s.

$ hubdev snapshot --json [--include=sites,services,php,caddy,docker,health]

{
  "schema": 1,                    // bumped on breaking change; plugin refuses newer majors
  "hubdev":   { "version": "1.28.0", "update_available": null },   // PROPOSED
  "caddy":    { "running": true, "version": "2.11.4", "routes": 15 },  // known
  "php":      [ { "version": "8.4", "default": true, "fpm_running": true } ], // known
  "services": [ /* the hubdev_list_services shape, minus `password` */ ],  // known
  "sites":    [ { "name", "domain", "driver", "php_version", "mode", "active",   // known
                 "tls", "route_present" } ],                             // PROPOSED
  "docker":   { "available": true, "containers": {...}, "reclaimable_bytes": 0 },
  "health":   { "checks": [ { "id", "level": "ok|warn|error", "label", "detail" } ] },
  "license":  { "plan": "free", "status": "active" }   // never the key
}

What the source changed here. Every known field already has a mcp.Bridge method behind it, so the read side is wiring rather than new logic. Only four things are genuinely missing from the Bridge and need adding: Caddy running/version/route count, Docker container counts and reclaimable bytes, backup totals, and license plan.

Every field is marked known (HubDev already computes it via mcp, doctor or caddy:status) or PROPOSED (new work in the Go core). Only the proposed ones carry schedule risk; a v1 that drops all of them still works.

Four rules

  • Two tiers. Cheap — caddy, php, services, sites — every 30 s closed, 5 s open. Expensive — docker, health, backups — every 30 s regardless, plus once on panel open.
  • A ~2 s TTL cache inside hubdev, so a burst of calls does not hammer Docker.
  • Never serialise secrets. services.yml holds plaintext passwords and license.json holds the key. Both stripped, with a test that asserts it.
  • Mutations answer JSON too — {"ok":false,"error":"…"}, exit code mirroring it, and NDJSON progress lines for image pulls, last line wins.

06Scope

A glance, and a deliberate refusal to be a console

In the bar

The HubDev mark, monochrome, taking the bar foreground. A coloured dot only when something is wrong:

Red Caddy stopped · default PHP FPM stopped · HubDev not answering
Yellow an auto_start service is stopped · an active site has no Caddy route · a certificate expires within 14 days · Docker unavailable while docker-mode services are enabled · license not active
None healthy — the bar says nothing at all

In the panel

Two views behind one toggle, remembered in the bar's settings: a dense table (~420 px) and three columns (~760 px). Environment — Caddy, every installed PHP with the default in bold, Docker, hosts entries, TLD resolution, SSL expiry, version. Sites, Services, and Needs attention, in plain words, drawn only when non-empty.

Sizing is a real constraint here. This machine has 15 sites, 8 services and 2 PHP versions — roughly 3× what lerd Glance assumes. The panel caps at 70% of screen height, sections scroll independently, and inactive sites collapse behind a count. The 15-site fixture is the acceptance gate for the columns view.

Actions, and what is refused

RowVerbsCLI

Out of scope for v1, deliberately: site:new, site:clone, backup:restore, service:reset, artisan, composer, php:install, marketplace installs, security scans — interactive, destructive, or minutes long. And no log surfaces: logs leak tokens into a bar panel. The escape hatches are Open HubDev GUI and Open terminal at site, which is honest about where that work belongs.

Safety model

  • Every action is a fixed argv array, never a shell string, and the subject is validated against the current snapshot before use.
  • Confirm-gate, inline and two-step for anything that stops something in use — the icon becomes a labelled "Sure?" for 4 s, and only the second click sends. No modal; the panel closes on Escape and a modal would fight that.
  • No sudo, ever. A verb that could prompt for a password would hang a QML Process invisibly inside the long-running shell. Any verb that can escalate is excluded from the allowlist regardless of how useful it is.

07Phases

Seven phases, two of them in parallel

  1. P0

    Readiness spike ≈1 session

    Verification only — everything downstream assumes these answers. Can a plugin import Quickshell.Io and use Process? Which verbs can trigger sudo? Does hubdev status take a lock on the config directory? Latency with services actually running?

    Exit criteriaA number, from hubdev, in the Quattro bar.

  2. P1

    The JSON contract ≈1–2 sessions · revised down

    Repo is cloned. Add cli_snapshot.go calling the existing mcp.Bridge reads; extend the Bridge with the four missing pieces; add tiers and a TTL cache; fix NO_COLOR; strip secrets; export fixtures.

    Exit criteriahubdev snapshot --json | jq on a fresh machine.

  3. P2

    Read-only plugin v0.1 ≈2 sessions

    Manifest, widget, source seam, model, theme, mark. Polling with coalescing, suspension when hidden, and backoff when HubDev is absent. Tests green against every fixture.

    Exit criteriaStop Caddy → the dot turns red within 30 s and the tooltip says why.

  4. P3

    Panel v0.2 ≈3–4 sessions

    Both views, the toggle bound to v, settings persistence, all sections, scroll and collapse for 15+ sites.

  5. P4

    Actions v0.3 ≈2–3 sessions

    Allowlist, argv construction, snapshot validation, confirm-gates, per-action timeouts, spinner and refusal states, refresh burst.

  6. P5

    Publish v1.0 ≈1 session

    README, LICENSE, preview, CI running node --test + qmllint + omarchy plugin validate, marketplace submission.

  7. P6

    The daemon optional

    Only if polling proves insufficient. SourceHttp.js replaces SourceJson.js and nothing else changes — which is the whole point of the seam.

P1 and P2 run in parallel. The fixtures are the contract — hand-written first from the mcp output that already exists, so neither side blocks the other.

09The grill

Thirteen challenges. Seven changed the plan.

Each one, the verdict, and where the plan moved.

G1Revised

"The critical path runs through a repo you cannot see."

hubdev snapshot --json is invented, and Phase 2 was written as if it depended on Phase 1. Valid, and the phase ordering was wrong. Phases 1 and 2 now run in parallel; the fixtures are the contract, hand-written from the mcp output that demonstrably already exists.

Update, post-grill: the premise collapsed entirely — the CLI source is fully available and is now cloned at devhub-go. Reading it showed the contract is smaller than assumed (see §01), so R4 drops from a real risk to a scheduling note and Phase 1 halves.

→ §07 phases, R4
G2Revised

"You bet the whole plan on Process, which the docs never mention."

The original mitigation — "pivot to a daemon" — moved weeks of work into another repo on a coin flip. Valid, and the mitigation was lazy. There is a middle rung: XHR is proven available and reads file://, so a systemd user timer writing ~/.cache/hubdev/snapshot.json gives a read-only plugin with no Process and no daemon.

→ §04 the ladder, R1
G3Revised

"Polling a CLI at 5 s is not the same as polling HTTP at 5 s."

lerd's 5 s is seven round-trips to a running process. Ours is a Go binary cold-start plus Docker probes, already 374 ms with everything stopped. Valid. Two explicit tiers, and the expensive one never runs at 5 s.

→ §05 four rules
G4Revised

"lerd Glance is designed for a handful of sites. You have fifteen."

Three columns at 760 px with 15 sites, 8 services and 2 PHP versions does not fit on screen. Valid. Height cap, independent scroll, collapse behind counts, and the 15-site fixture as the acceptance gate.

→ §06 sizing
G5Revised

"Your contract mixes fields HubDev has with fields you made up."

route_present, tls and update_available are inventions; services[] and caddy are real. Presenting them uniformly hides where the schedule risk is. Valid. Every field is now marked known or PROPOSED.

→ §05 the contract
G6Revised

"'Confirm-gate' is not a design."

A modal in a panel that closes on Escape fights the panel. Valid. Inline two-step instead. The challenge also caught that site:stop removes the Caddy route, so it belongs behind the gate too.

→ §06 safety model
G7Revised

"Nothing says how this survives the user's own theme."

This machine runs amber #F99957 on navy — amber sits next to the warning colour, so a colour-only warning state would be invisible here. Valid. State colour is hard-coded, chrome inherits qs.Ui.Style, and warning must be distinguishable by glyph as well as hue.

→ §06 theming
G8Rejected as the plan

"Why not read HubDev's config files and skip the CLI entirely?"

It works today, with zero HubDev changes. But it reimplements HubDev's own resolution logic — which service owns a port, what makes a site active, how mode interacts with Docker — in a second place, in JavaScript, where it will silently drift from the Go that defines it. Kept as SourceFiles.js for the spike. One release changes a key and the bar lies.

G9Rejected

"Why not talk to hubdev mcp? The JSON is already there."

MCP is an agent protocol with session semantics, and HubDev ships a master switch whose entire purpose is refusing new sessions. A bar widget that dies when the user runs mcp:disable — or holds a session open forever so the connected-client list is permanently wrong — is a misuse of that surface.

G10Answered

"This duplicates the HubDev GUI. What is it actually for?"

The GUI is a window that must be raised, focused and dismissed; this is a dot in a bar already on screen. The scope split makes the distinction real rather than rhetorical — the widget deliberately refuses everything long or destructive, with explicit hand-offs to the GUI and the terminal.

G11Upheld

"A sudo prompt inside a QML Process hangs the shell with no visible cause."

Already gated, and at the right severity. sudo -n fails on this machine today, and HubDev has installed a sudoers rule whose contents could not be read without a password. Phase 0 enumerates every escalating verb.

G12Accepted

"No QML is tested. At all."

Deliberate — the same trade lerd makes. Every rule worth getting wrong lives in Model.js and Actions.js, which run under node --test. QML is covered by the docs' manual checklist as the P3/P4 exit gate: click, Escape, summon/hide, disable and re-enable, shell restart, removal.

G13Answered

"Should this even be a bar-widget?"

Yes. menu and overlay are summoned; a glance must be already visible or it is not a glance. Worth noting for later: a service kind could expose HubDev state as a headless singleton other plugins and keybinds could read.

Residual risk after the grill

The plan survives its two worst cases — a late CLI contract and no Process — with a reduced but real v1 in both.

Reading devhub-go then closed the third: there is no cross-process lock, so polling reads cannot contend with the GUI and the refresh model stands as designed. What the source put in its place is smaller but real — writes are last-writer-wins, with no file lock between the widget, the CLI and the GUI. That is pre-existing HubDev behaviour rather than something this plugin introduces, but the plugin makes it easier to hit.

One unknown now carries the plan: R1 — whether an Omarchy plugin may use Quickshell.Io.Process. It is the first thing Phase 0 answers, it decides between a full plugin and a read-only one, and nothing else should be built before it.

10Open questions

Four, one already closed

01

Is the HubDev CLI source yours to change? Answered

Full access to the hubdev organization including the CLI source and binary — it is simply not cloned on this machine (Phase 1, step 0). The remaining question is narrower: which HubDev release carries snapshot --json, since the plugin must version-gate against it.

02

Public or personal?

A marketplace plugin makes this part of HubDev's product story, and a direct answer to lerd Glance. A personal plugin skips Phase 5 entirely.

03

Read-only v1, or actions from the start?

Read-only halves the surface and removes R3 entirely.

04

Does the widget ever need to show a remote HubDev?

If yes, that argues for the daemon now rather than at Phase 6.
